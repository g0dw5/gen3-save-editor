# ROM-specific cheat codes — implementation plan / 金手指实现方案

Status: proposed, not implemented. Written on 2026-09-21. This document is a
development handoff, not a compatibility claim or a list of working codes.

状态：仅方案，尚未实现。用户计划稍后按本文启动开发；现在不修改功能、不更新
版本号、不打安装包，也不定时自动启动开发。后续启动时先读取最新 AGENTS.md、
工作区状态与本文件，保留期间其他任务的改动。

## 1. 产品目标与边界

加载支持的精确版本 ROM 后，无需加载存档，即可查看该 ROM 已验证的金手指功能，
选择参数、阅读操作步骤并复制代码到模拟器。功能定位是离线资料与代码生成工具。

- ROM 决定地址、数据含义、执行时机与游戏行为；金手指格式负责表达这些操作。
  模拟器兼容性是格式与指令实现的兼容性，不应反过来决定 ROM 功能的组织方式。
- 不存在可直接从 ROM 枚举出的“所有金手指表”。每项能力都需要研究和验证，
  页面列的是项目已支持的功能，不宣称穷举 ROM 的全部可能修改。
- 不连接用户正在运行的模拟器，不自动启用金手指，不修改打开的 ROM 或存档。
  复制代码也不进入存档的撤销/重做记录。
- 不把未核实的网络代码、原版绿宝石代码或另一改版的代码当作可用功能发布。
- 首期不做任意地址编辑器、在线代码市场、自动下载代码库或通用 ARM 补丁编译器。
- 所有游戏内容继续从当前 ROM 读取。必要的地址、编码规则、补丁策略和兼容信息
  属于适配配置；不得把宝可梦、道具名称等提取后另建内置目录。

首批研究范围为目前已适配的三个精确配置：

| ROM | Profile ID | MD5 |
| --- | --- | --- |
| 漆黑的魅影 5.0EX+BW | `dark-phantom-5ex-bw` | `0d9b129f7dd76895f79bb47ad7dec2fe` |
| 漆黑的魅影 5.0EX+DP | `dark-phantom-5ex-dp` | `cb2940215f4dafb1bef133c3af379f44` |
| 西班牙火箭队 2.1 汉化版 | `rocket-21-zh` | `59c658a1081f542086de1060bb65f0b3` |

以上标识取自当前 `profile.rs`，实施时再次核对。BW/DP 可以共享规则实现，但
必须各自验证；西班牙火箭队不得隐式继承另一 ROM 的地址或功能。未知 MD5
保持现有拒绝加载规则，不新增“强行套用”入口。

## 2. 首期研究清单与交付门槛

下表是研究优先级，不是已经支持或保证能实现的清单。

| 顺序 | 候选能力 | 需要证明的行为 | 阶段处理 |
| --- | --- | --- | --- |
| 1 | 暂停普通随机遇敌 | 只影响对应野外触发，保留脚本战斗、训练家战斗和定点事件 | 优先寻找可独立验证的最小闭环 |
| 2 | 指定下一次普通野生相遇的宝可梦及等级 | 在生成个体之前修改选择结果，由游戏原生流程生成完整个体；明确草丛、冲浪、钓鱼等覆盖范围 | 核心候选，逐种相遇方式验证 |
| 3 | 调整普通野外遇敌频率 | 不改变定点、剧情、逃跑等其他判定；明确与暂停遇敌互斥 | 有独立证据再加入 |
| 4 | 捕捉、孵蛋、经验等省时能力 | 修改判定还是结果、永久影响范围、引擎限制与关闭行为 | 后续研究，不因名称常见直接承诺 |
| 5 | 金钱、道具、个体值等持久数据 | 动态存档块、加密、位所有权和校验的一致性 | 后置；已有存档修改器可先满足需求 |

穿墙、剧情标志、传送、直接覆盖队伍/盒子加密数据不纳入首期。暂不支持某项
不代表禁止未来扩展；先把它与有证据的能力分开。

开发顺序先拿一个功能跑通 ROM 研究 → 编码 → 实机模拟器执行 → 关闭恢复 →
存档再读，再扩展条目和页面。若某 ROM 没有任何通过验收的条目，明确显示
“此版本尚无已验证金手指”，不能为了填充列表降低验证标准。

之前会话提供过的胡说树代码，用户反馈没有生效；其本身不能作为兼容证据。
天然鸟损坏的根因也未被证明是金手指，不将推测写成已确认结论。后续测试必须
能发现 PID、高位字节、校验和等非预期变化。

### 必做专项：复核胡说树旧代码的版本适配

用户明确提出的待验证假设：之前失败可能是网上代码只适用于另一个版本，
不适用于正在玩的这份 ROM。此项属于阶段 A 的必做调查，不能被新功能替代。

现有本地会话审计记录：2026-09-12 14:05:23（北京时间）曾提供遇宠开启码
`0146DCEA 3E32A31D` 和标为 CodeBreaker 的 `83007E28 00B9`；14:20:36 用户
反馈未生效。这里仅保存失败样本用于诊断，不是推荐代码，也没有确认前者的格式。

调查步骤与结论要求：

1. 追溯当时给出代码的原始会话与来源，确认网站声称适用的 ROM、版本和格式。
   找不到来源时明确写“原始适用版本未知”，不得把猜测包装成来源结论。
2. 按候选格式解析两段代码，确认是否混用了设备协议、是否需要分别导入，
   开启码究竟是补丁、条件还是其他操作；无法确定格式时保留不确定性。
3. 针对用户当前精确 BW MD5，跟踪实际读写地址、原生野生生成流程和代码触发
   时机；直接查当前 ROM 中 `0x00B9` 对应的物种，核实编号是否就是胡说树。
4. 在可观测模拟器与一次性测试副本上分别执行单段和合理的依赖组合，观察实际
   内存写入以及普通相遇结果，区分“没有执行”“写了但游戏没用到”“编号不符”。
   不在用户当前游玩存档上尝试。若来源能确定且本地存在合法可用的对应版本，
   可追加对照；没有参考 ROM 不影响证明当前 ROM 中的地址/流程不匹配。
5. 分别给出版本不匹配、格式/主码问题、启用方式与触发场景问题的证据。可能
   多个原因并存；不能仅因为旧码无效就断言版本错误，也不能仅因新码有效就
   声称已找到旧码失效根因。手机端当时操作无法复原时明确说明。

交付一份公开可读的复核说明和自动化回归样例；私人会话、存档、完整内存转储
保留在本地。胡说树代码失效与天然鸟坏蛋是两个独立问题，除非获得直接因果证据，
不能将本次结果当成天然鸟损坏原因。

## 3. 交互方案

沿用 ROM 资料的非模态窗口，在资料导航中加入“金手指”。打开 ROM 即可使用，
不要求存档，也不把“修改存档”伪装成金手指功能。

桌面布局：左侧可搜索的功能列表，右侧为功能详情。窄窗口改成列表与详情的
单栏切换，代码区允许横向滚动；复制按钮和必要操作说明保持容易找到。

详情的内容顺序：

1. 功能名和一句话作用，例如“指定普通野生相遇”，明确不覆盖哪些触发方式。
2. 参数：宝可梦、等级等使用已有搜索控件，名称和形态显示来自当前 ROM。
   不把所有可读取物种都默认当成可生成的野生个体；蛋、占位条目、战斗临时形态
   等必须由该功能的已验证规则筛选，说明不能选择的原因。
3. 代码格式选择，默认该功能首选且已验证的格式；可展开模拟器兼容记录。
   模拟器名称是使用帮助，不是必须先选的主要步骤。
4. 具体使用步骤：在哪个游戏状态启用、是否按键触发、何时关闭、是否需要重启。
5. 代码和“一键复制”；有前置代码时按实际导入方式分组，并分别解释启用次序。
6. 已验证范围、持久影响与冲突提示；研究地址与技术证据放在折叠详情中。

默认仅展示已验证条目。未验证候选留在开发研究资料中，不给普通用户一个可复制
但只是“也许能用”的代码按钮。已验证条目仅对尚未测试的其他模拟器，显示
“该模拟器未实测”，不能显示已兼容。

重复点击生成应得到相同代码，不修改任何数据。切换 ROM 时清空选中参数、代码、
复制状态与过期请求；切换语言只翻译 UI 文案，不覆盖 ROM 原名。中英文同步交付。

## 4. 架构与复用边界

沿用现有三层结构；CLI、桌面和未来浏览器端共用 Rust 核心，不在 React 中生成
地址或拼接实际金手指指令。建议增量引入 `crates/gen3-core/src/cheats/`，随着
首个经过验证的功能拆分，避免在研究前堆出大型通用框架。

### 4.1 三个独立维度

| 维度 | 职责 | 复用条件 |
| --- | --- | --- |
| 游戏语义 / recipe | 某个功能修改哪个流程，参数约束、触发和关闭方式 | 执行逻辑和数据结构一致才共享 |
| ROM binding | 精确指纹、RAM 地址或指针规则、ROM 例程与补丁位置、宽度和边界 | 地址差异用配置；引擎差异用独立规则 |
| 格式 encoder | 把受支持的操作编码成指定 CodeBreaker/GameShark 等指令 | 与宝可梦数据和 ROM 名称无关 |

不能承诺以后只填偏移就能适配。固定 RAM 半字写可以共享编码；动态指针、
调用时机、指令补丁、物种生成规则的差异需要新的可测试策略。不可在 UI 堆叠
`if rocket / if bw` 来处理这些差异。

### 4.2 建议的核心数据模型

这是接口设计草案，按首个闭环结果精简，不预先固定 JSON 文件格式。

- `CheatDefinition`：稳定 ID、文案 key、分类、参数类型、适配规则 ID。
- `CheatBinding`：精确 profile、地址/指针与目标宽度、必要的 ROM 结构检查、
  支持格式、前置组件与冲突关系。静态配置只存必要引擎知识。
- `CheatPlan`：受限制的操作序列、参数值、触发与生命周期语义。
  先实现首批功能实际需要的写入和条件，未实现的指令显式报错。
- `GeneratedCheat`：ROM 指纹、功能与规则修订号、规范化参数、格式及格式版本、
  需要分别导入的代码块、启用/关闭步骤、影响说明和验证摘要。
- `VerificationRecord`：精确 ROM、功能修订、格式、参数范围、测试项、
  执行引擎及版本、结果和证据来源。验证必须跟随实际规则修订失效或重新确认。

完整实验日志留在研究文件或本地证据目录。发布包只带必要规则、摘要与说明，
不带 ROM、存档、截图资源、研究缓存或未经审核的候选代码库。

### 4.3 API、CLI 与 UI 接入

建议新增只读 API：

```text
cheats
  -> 当前 ROM 已验证的功能、参数定义与格式

cheat_code { expected_rom_md5, cheat_id, parameters, format }
  -> GeneratedCheat
```

核心从当前 `Rom` 选择 binding，不接受客户端传入地址或冒充 profile。
`expected_rom_md5` 不匹配当前会话即拒绝，避免切换 ROM 后旧表单生成新版本代码。
参数在后端再次校验：拒绝 null、负数、小数、溢出、无效 ID 和不受支持的形态。
实际可选范围来自 ROM 数据与已经验证的 recipe 约束，而非 UI 自行猜测。

CLI 建议增加 `gen3 cheats ROM` 与 `gen3 cheat-code ROM ...`，支持结构化结果
用于测试和 agent 使用；生成不需要 SAVE 参数。

主要集成点：`profile.rs` / `adapter.rs` 提供按版本的能力绑定，`rom.rs` 暴露
只读服务，`app.rs` 统一派发；`ui/types.ts`、`ui/ReferenceWindow.tsx`、
新 `ui/CheatReference.tsx`、`ui/i18n.tsx` 提供共用页面。`Session` 的存档事务
路径不参与生成过程，不需要为了此功能扩展存档写入权限。

## 5. 运行时语义：研究必须解决的问题

- **存档偏移不等于 RAM 地址。** 必须确认存档块指针是否重定位、目标是否加密、
  生效状态以及指令能否表达必要的间接寻址。无法表达时，该格式不支持此功能；
  不能固定一次运行观察到的地址，也不能要求加载 `.sav` 来推断当前 RAM 指针。
- **RAM 改值与修改 ROM 指令不同。** 分别研究数据写入、ROM 补丁、主码/钩子
  的执行时机；选择所需最小机制，不默认附加一个网上通用“主码”。
- **关闭不等于撤销。** RAM 持续写停用后不一定恢复旧值；补丁移除可能依赖引擎，
  即时存档还可能保存修改后的状态。每项功能要实测关闭、冷启动和读档行为，
  写清自然恢复、必须重启或已产生持久结果，不能笼统写“关掉就恢复”。
- **个体生成必须完整。** 指定相遇优先改原生生成函数的输入，验证 ROM 的等级、
  招式、性别、特性、形态和加密记录生成，不直接覆盖一个已生成的个体编号。
- **条件和频率必须明确。** 每帧、按键、进入战斗等不是等价语义；确认写宽、
  对齐、范围、按键组合以及相邻字节不会被一起覆盖。
- **依赖和冲突必须显式。** 共用钩子、重叠写入、互斥目的均需要说明。首期按
  单功能独立使用验证；不声称能检测用户在模拟器里另外启用的金手指。
  只有实际测试过的组合才列为可同时开启。
- **代码格式不能含糊。** GameShark/Action Replay 不同版本不能仅用一个泛称
  混合。先选择能覆盖首项能力的明确格式，实现其所需子集，再考虑其他格式；
  不做未经证明的字符串“格式转换”。

## 6. 证据与测试标准

“已支持”要求 ROM 语义证据、代码编码证据与完整执行证据相互对应。单纯能复制、
模拟器接受代码或 Unicorn 函数探针通过，都不足以单独证明功能已可发布。

| 层次 | 需要的证据 | 可对外说明 |
| --- | --- | --- |
| 研究候选 | 来源与待验证假设 | 仅开发资料，不提供正式可复制功能 |
| 原生逻辑验证 | 精确 ROM 例程、读写目标及探针对照 | 说明已验证哪些逻辑，仍不称完整可用 |
| 代码执行验证 | 真实代码经指定引擎解析执行，正例、负例、启停均通过 | 支持该 ROM / 功能 / 格式 / 已测引擎组合 |
| 应用实测 | 指定模拟器应用版本实际导入、游戏操作和退出复查 | 仅此时标记该应用已实测 |

桌面 mGBA 或其他可观测引擎可作为首个参考执行环境，但其通过不能自动写成
Delta/Manic EMU 已实测。手机端如当前无法执行，保留明确范围，待用户测试反馈；
不因此阻止其他已完成组合的交付。

测试要求：

1. 无 ROM 的公开测试：编码黄金向量、宽度/字节序、条件范围、参数边界、依赖
   展开顺序、未知指令拒绝、错 ROM 拒绝、不同 profile 不串用规则。不能只用
   同一自制 encoder/decoder 互证，至少对照独立实现或已知规范向量。
2. 本地 ROM 探针：对照实际原生流程，记录 ROM MD5、关键地址及输入/输出。
   最小、最大、扩展物种编号及有效形态等代表性参数均覆盖；未验证范围不开放。
3. 模拟器执行：从干净启动、独立测试存档开始，启用一次只测一项，覆盖支持的
   相遇类型、场景切换、战斗结束、关闭和重新启动。实际解析器应执行生成的文本
   代码，不能用调试器直接写内存代替该测试。
4. 持久性复查：若能捕获宝可梦或产生游戏内保存，比较前后个体、库存、进度和
   校验结果，白名单允许正常游戏推进产生的差异。至少包含 PID 高位非零、
   不同加密排列的哨兵个体，确认无无关记录损坏。测试仅使用副本。
5. 三 ROM 回归：BW → 西班牙火箭队 → DP 切换、旧异步响应、不同名称/编号/形态、
   未支持功能无回退；原有读写、拖拽、保存回读与精确指纹检查继续通过。
6. UI：无存档可用、搜索、参数无效、代码复制、前置代码分组、中英文、窄窗口、
   切换 ROM 后复制不会得到旧代码。输入变化立即使旧代码失效，生成中不可误复制。

研究证据使用项目现有 `scripts/verify_*.py` 模式，建议新增
`scripts/verify_cheat_codes.py` 和 `scripts/test_cheat_codes_ui.py`。
精确结果表按 ROM × 功能 × 格式 × 引擎 × 参数范围维护；每个功能有稳定证据 ID，
不在 README 写无法追溯的笼统“全部通过”。

## 7. 开发阶段与完成条件

### 阶段 A：验证一个真实闭环

- 核对工作区、当前版本与三个 ROM 指纹；阅读已有原生探针和存档完整性案例。
- 完成上面的胡说树旧代码专项，验证用户提出的版本不适配假设并记录证据边界。
- 从优先级 1/2 中选择可证明的能力，记录地址来源、目标原生流程与生命周期。
- 核对目标格式的公开实现，用生成的代码完成一次参考模拟器执行和保存再读。
- 输出每份 ROM 的可行性表与明确的不支持原因。无法完成闭环时如实报告研究阻碍，
  不用空页面或猜测代码冒充交付。

### 阶段 B：核心和命令行

- 从已验证功能抽取最小 recipe、binding 和 encoder，接入纯读取 API 与 CLI。
- 加入参数约束、依赖/冲突元数据、验证摘要和 profile 隔离测试。
- 新 recipe 不更改旧 recipe 语义；不同引擎规则分别组合，不复制整套代码。

### 阶段 C：资料窗口

- 接入共用页面、ROM 名称搜索、参数选择、生成/复制和清晰的步骤文案。
- 完成中英文及窄窗口检查；保留既有存档编辑界面和交互。
- 公开状态只反映验收通过的功能，未支持 ROM 显示明确空状态。

### 阶段 D：扩展和回归

- 将已证明能共享的功能扩到另外两份 ROM，分别验收；继续优先级清单。
- 运行 Rust 测试与 lint、TypeScript 检查、相关 UI 和多 ROM 回归；按改动范围
  选择必要测试，遇到新失败继续修复，不反复运行无关检查。
- 更新中英文使用说明与当前未发布版本的 ChangeLog，记录实际覆盖和限制。
- 按有意义的阶段及时提交；用户明确要求时才打发布包、改版本或发布。

完成条件：至少交付一个经过完整执行验证的功能及其可追溯范围；三个 ROM 都有
明确结果，无法支持的不得被 UI 隐藏成通用成功。代码生成不触碰源 ROM/存档，
原有跨 ROM 编辑与导出回归通过。其他候选能力逐项扩展，不追求凑数量。
